# ADR-0008: 初代ザ・コンビニ(PS1版)の完全な忠実再現を優先する

Status: Accepted
Date: 2026-10-09

Supersedes: ADR-0007(店舗評価の移植作業中にユーザーから方針強化の指示があったため)

## Context

ADR-0007は「PS1解析データを一次参考資料として扱い、入手可能な数式は優先して移植するが、
独自のバランス数値は本プロジェクトの文脈で再設計してよい」という、やや両立的な方針だった。

店舗評価(店舗評価の増減、`design/ps1-reference/algorithms.md` §4.2)の移植作業中、
以下2点をユーザーに確認した。

1. 原作の5条件(価格・サービス・警備・清潔さ・売上)のうち、本プロジェクトに
   対応する数値がない「サービス」「警備」をどう扱うか。
   → ユーザー回答:「3条件のみ移植(推奨)」を選択。
2. 店舗評価の更新頻度(本プロジェクトには「月」の概念がまだない)。
   → ユーザー回答:「いやいや、まずは初代ザ・コンビニを忠実に再現するので、
     月は4日だろ。MDに完全再現と書かれていないのであればそこは修正しておけ。
     まずは完全に忠実に再現だ」

この回答は、ADR-0007の「独自の文脈で再設計してよい」という緩い方針では不十分で、
**まず忠実再現を優先する**という、より強い方針転換の指示である。

### 「1ヶ月=4日」の裏付け

ユーザーの指摘を受け、アップロード元ファイル(`Conveni-PS1-Claude-Handoff.md`)を
直接再確認した。

- 内部時刻変換(`0x80019EB4`): `月内4段階 = (t // 1440) % 4 + 1`、`時 = (t // 60) % 24`。
  1段階 = 1440時刻単位 = 24時間相当であり、1ヶ月は4段階で構成される。
- イベント予約処理: 「分=0、時=0、月内段階=1のとき: 月次報告イベント(種別2)」
  「さらに月=1のとき: 総合評価イベント(種別3)」であり、**月次報告と年始の
  総合評価は別イベント**。店舗評価の増減(§4.2)はこの月次報告イベント側で
  走ると判断する。
- 一方、元ファイルは「月内段階を現実の暦の「日」と同一視していない」と明記して
  おり、段階=UI上の「日」表示と断定したものではない。構造上は24時間相当サイクル
  ×4=1ヶ月、という点のみが確認済みの事実である。

本プロジェクトには元々「月」の概念がなかったため、1ヶ月 = 本プロジェクトの
4日、として新規定義する(`MONTH_LENGTH_DAYS = 4`、`src/simulation/storeRating.ts`)。

## Decision

1. **これ以降、特に明記のない限り、PS1版のアルゴリズム・数値・周期は
   そのまま移植することを優先する。** 本プロジェクト独自の数値で上書きする
   場合は、その理由(対応する原作データが存在しない、原作の数値がそのまま
   使えない具体的な理由がある等)を各ADRまたはコードコメントに明記する。
   ADR-0007の「独自の文脈で再設計してよい」という表現は、本ADRにより
   「原作データがある箇所は原則そのまま使う」へ強化される。
2. `design/PRINCIPLES.md`の「史実を再現するだけでなく、別のコンビニ史を
   作れる」(原則12)は撤回しない。ただし優先順位としては、**まず原作の
   忠実な再現を土台として組み立て、そのうえでプレイヤーの選択による分岐を
   実装する**、という順序であることを明記する。
3. 店舗評価の移植スコープ:
   - 価格・清潔さ・売上の3条件のみを移植する(サービス・警備は未実装のため
     対象外。将来、店員AI・防犯設備を移植した時点で追加を検討する)。
   - 「3条件中3条件達成で+5点」という、原作の定数(5条件中3条件)を
     そのまま使った結果、本実装では実質「3条件すべて達成」が+5点の条件に
     なる(原作より厳しい)。これは数値を独自に補正しない方針上の既知の
     帰結であり、バグではない。
   - 評価更新の周期は`MONTH_LENGTH_DAYS = 4`(本プロジェクトの日数で4日)。
   - 売上のしきい値(50万円〜1,500万円)は原作の円単位をそのまま使用する。
     実測(シード1977、30日シナリオ)で本プロジェクトの4日あたり売上は
     約100万円であり、原作のしきい値と同じ桁に収まるため、再スケーリング
     していない。

## Consequences

- `src/simulation/storeRating.ts`に`MONTH_LENGTH_DAYS`と
  `applyMonthlyRatingUpdate()`を実装し、`src/simulation/simulation.ts`の
  日次締め処理に組み込んだ(4日ごとに`playerStore.reputation`を更新し、
  `DailyReport.storeRatingUpdate`に内訳を記録)。
- 今後、他システム(店員AI・街の成長・ライバルAI・財務)を移植する際も、
  「原作にある数式・周期はまず忠実に使う」をデフォルトの判断基準とする。
  独自再設計が必要な場合は、その都度ユーザーに確認し、理由を記録する。
- 競合店舗(competitorStores)の評価は、現在の実装では更新されない
  (競合店舗の内部売上・清潔さをシミュレーションしていないため)。これは
  スコープ外として明記し、将来の競合AI強化時に再検討する。
