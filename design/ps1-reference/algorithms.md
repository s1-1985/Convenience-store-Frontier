# 初代ザ・コンビニ(PS1版)— 抽出済みアルゴリズム

出典・注意事項は`README.md`参照。各見出しの括弧内は解析元ファイル中の関数アドレス。

## 1. 乱数生成(`0x8007E648`、シード設定`0x8007E678`)

```text
seed = (seed × 1103515245 + 12345) mod 2^32
戻り値 = (seed >> 16) & 32767      # 0〜32767
```

状態は単一グローバル`0x800D6270`。シード1の最初の戻り値は16838(検証値)。
多くの判定式は`乱数 % 100 + 1`(1〜100)または`乱数 % N`の形で消費される。

## 2. 客需要の生成(`0x8002619C`〜`0x80027328`)

### 2.1 月別天候(画面名未確定、コード内では"weather"と仮称)の抽選

乱数1〜100を引き、月別の4閾値表(`demand-tables.json`に収録、例: 1月=30/60/80/95、
6月=1/10/40/90)と比較する。

```text
roll <= 閾値1: weather = 0(追加乱数なし)
roll <= 閾値2: weather = R%19+1 (1〜19)       # 追加で乱数を1回引く
roll <= 閾値3: weather = R%20+20 (20〜39)
roll <= 閾値4: weather = R%20+40 (40〜59)
それ以外:      weather = R%20+60 (60〜79)
```

### 2.2 客候補の除外判定(通常経路、バイパスフラグ`0x800CDA00`が0のとき)

街60×50マスを走査し、各マスの客グループ(最大5組の`(プロファイルID, 数量)`)に
ついて、各客候補(144プロファイル)を次の順で判定する。

1. `プロファイル+0x0D + 20 < weather` なら除外(等しい場合は通る)。
2. 主商品の季節判定(下記2.4)が2(除外)を返したら除外。
3. 乱数1〜100が`プロファイル+0x15+区分`の符号付きbyte以下なら通る。区分は
   `月×4+段階-1`から求める出現率テーブル値。

バイパスフラグが非0のときはこの3条件すべてをスキップする(weather抽選と
後段の店舗選択乱数は実行される)。

### 2.3 行き先店舗の選択(`0x80026A64`)

候補店舗順リスト(最大10、`0x800CE61C`)の各店舗について、まず乱数を1回引く。

```text
1. roll1..100 <= store.rating + 20                    # 不合格なら除外
2. 営業時間表[store.schedule][profile+2] != 0          # 不合格なら除外
3. profile+0x0C==3 の場合のみ: store.capacity > 0       # 特定客種別の追加条件
4. store.stock[profile.主商品] > 0
5. 距離 D <= 客区分別上限 [20,40,60,70][profile+0x0C]
   D = max(storeLeft-X, X-storeRight) + max(storeTop-Y, Y-storeBottom)
```

商品在庫が0の店舗でも乱数は1回消費する。距離・在庫判定は店舗を通過しても
除外されても必ず行われるわけではなく、早期にfailした店舗の距離作業値は
更新されない。

候補が複数残った場合、以下の比較点が最大の店舗を選ぶ(距離は0〜100へ正規化、
`L=0,H=110`が通常値)。

```text
距離点 = 100 - trunc((D-L)*100/(H-L))     # H==Lなら0
比較点 = 価格点×profile.価格重み + 距離点×profile.距離重み + 防犯点×profile.防犯重み
```

同点時のタイブレーク: ①主商品在庫が多い店舗 → ②`store.rating`が高い店舗 →
③リスト内で先の店舗。候補ゼロなら店舗選択なし(需要消滅)。
**乱数で候補を絞った後、加重比較点を最大化する二段階選択であり、価格や距離に
乱数を直接掛ける抽選ではない。**

### 2.4 季節判定(`0x80027328`)

商品0〜26のみ対象(商品表+0x54の季節区分)。

| 区分 | 該当商品(例) | 優先季節 | 逆季節 |
|---|---|---|---|
| 1 | 冷たい飲料・アイス | 6/7/8月は通過 | 12/1/2月は抽選 |
| 2 | 温かい飲料・おでん・中華まん | 12/1/2月は通過 | 6/7/8月は抽選 |
| 0 | 上記以外 | 常に通過 | — |

逆季節月では乱数1〜100を引き、90以下なら除外(戻り値2)、91〜100なら通過
(戻り値0)。

## 3. 客の購買行動

### 3.1 客生成と数量集約(`0x800319AC`〜`0x80032AB0`)

空き客枠(店舗レベル別`[10,10,15,15,20,20]`)を探し、乱数`&3==0`のときだけ
生成する。乱数`%144`を開始点に144プロファイルを巡回走査し、時間帯表で有効かつ
残数が正の候補を探す。

```text
生成数量 = min(該当プロファイルの残数, 5)     # 1体の客が複数人分の需要を代表する
```

**この数量係数は「1棚あたりの購入個数」ではなく「客生成時に割り当てる集約数量」
である**(来店客数の画面表示と内部需要単位が1:1でないことを示唆する)。

### 3.2 複数候補・時間切れ(`0x800340FC`)

主商品がなくなった客は追加候補(プロファイル+0x9〜+0x11、最大3つ)へ進む。

```text
滞在期限切れ(現在時刻 >= 期限) なら状態3(退店系)
試行回数 >= 4 なら状態3
追加候補ごとに季節判定(2.4)を通過したものだけ選ぶ
```

最初の商品(入店時)には季節判定が掛からないが、追加候補には掛かる非対称性が
ある。

### 3.3 即時入金設備(`0x800360A0`)

設備表の先頭32bit値の下位8bitが2・3・5の設備(自販機等)は「その場で支払う」
分類。通常の棚は在庫がある限り候補になるが、この分類の設備は客の未精算額が
0のときのみ候補にする。

### 3.4 レジ精算の二段階抽選(`0x80038764`〜`0x80038878`)

```text
1. roll1..100 <= 店員の接客能力値(+0x1E)    # 失敗で戻り値1、ここで乱数消費終了
2. roll1..100 <= 客プロファイルの購入性向(+0x12)  # 失敗で戻り値1
3. 成功 → 店員能力更新(種別1)を実行し、戻り値0
```

第1段階で落ちたときは第2段階の乱数を消費しない(順序依存)。

### 3.5 待機カウンターと終了処理(`0x80035D58`)

```text
R = 乱数%100+1                      # 必ず1回引く
強制フラグなら即終了
カウンター(初期値 = プロファイル+0x11)が正なら:
  乱数を1回引き、&3==0 なら1減らす
まだ正なら継続(戻り値1)、0になったら終了側へ
```

終了側: 未精算額があれば`未精算額×数量係数`を収入計上。同じRを再利用し、
`Rが3の倍数`なら登録中の全店員の能力を種別-1(下限1まで減少)で更新、
`Rが10の倍数かつ店舗評価>=6`なら評価を1下げる。この2つは独立抽選ではなく
**同じRを共有する**。

## 4. 店舗評価

### 4.1 総合評価(年始イベント、`0x8003F7FC`〜`0x8003FE84`)

5項目×6段階(各0/4/8/12/16/20点)+ 対象店舗数×2点。

| 項目 | 0点 | 4点 | 8点 | 12点 | 16点 | 20点 |
|---|---:|---:|---:|---:|---:|---:|
| 累積来客数 | 5万未満 | 5万以上 | 10万以上 | 20万以上 | 40万以上 | 50万以上 |
| 年商合計(直前年) | 1億未満 | 1億以上 | 2億以上 | 3億以上 | 4億以上 | 6億以上 |
| 町人口 | 3000未満 | 3000以上 | 8000以上 | 14000以上 | 18000以上 | 20000以上 |
| 店舗評価平均 | 10未満 | 10以上 | 30以上 | 50以上 | 70以上 | 90以上 |

```text
総合評価 = min(100, 店舗数×2 + 上記4項目の得点合計)
```

8店舗で他4項目が満点なら100点に到達する(10店舗必須ではない)。

### 4.2 店舗評価の増減(`0x800282FC`〜`0x80028A94`)

現在評価を20で割った段階(0〜5)ごとに、5条件の改善/悪化しきい値が変わる
(評価が高いほど基準が厳しくなる)。

| 内部指標 | 0〜19 | 20〜39 | 40〜59 | 60〜79 | 80〜99 | 100 |
|---|---:|---:|---:|---:|---:|---:|
| 価格: 以下で改善達成 | 99 | 95 | 90 | 85 | 80 | 70 |
| サービス: 以上で改善達成 | 50 | 60 | 70 | 80 | 90 | 100 |
| 警備: 以上で改善達成 | 70 | 75 | 80 | 85 | 90 | 100 |
| 清潔さ: 以上で改善達成 | 80 | 85 | 90 | 95 | 100 | 100 |
| 売上: 以上で改善達成(円) | 3,000,000 | 5,000,000 | 7,000,000 | 9,000,000 | 10,000,000 | 15,000,000 |
| 価格: 超えたら悪化 | 100 | 100 | 100 | 100 | 100 | 100 |
| サービス: 未満で悪化 | 30 | 40 | 50 | 60 | 70 | 80 |
| 警備: 未満で悪化 | 50 | 55 | 60 | 65 | 70 | 80 |
| 清潔さ: 未満で悪化 | 75 | 80 | 85 | 90 | 95 | 100 |
| 売上: 未満で悪化(円) | 500,000 | 1,000,000 | 1,500,000 | 2,000,000 | 2,500,000 | 3,000,000 |

```text
良好数 = 改善達成の条件数(0〜5)
悪化数 = 悪化該当の条件数(0〜5)
更新後評価 = clamp(更新前評価 - 悪化数 + (良好数>=3 なら5点、それ以外0点), 5, 100)
```

直前に万引き被害額(`+0x118C`)が非0なら、この中心計算の前に評価を1下げる
別処理がある。

### 4.3 店舗評価補助式(清潔さ・近隣・防犯)

```text
清潔さスコア = min(100, trunc(店員清掃能力の合計×100 / [150,150,165,165,180,180][店舗レベル]))
サービス・近隣スコア = min(100, trunc(店員サービス能力の合計×100 / [250,250,275,275,300,300][店舗レベル])
                          + 近隣7マス拡張内の街タイル加点(60〜63番=+10/マス、64〜69番=+5/マス))
防犯集計 = min(100, 割当店員の防犯能力平均(0除算回避) + 設備加算(防犯設備種別45=+2、46=+4、47=+30))
```

価格・防犯の正規化は店舗間で**持ち越しが発生する**(各店舗ループ後に累計を
現在件数で割った値を次店舗の加算開始値にする)、という原作特有の癖がある
(詳細はHANDOFF原文参照、再現には注意が必要)。

## 5. 店員AI

### 5.1 仕事選択の優先順位(`0x800371E0`〜`0x80037380`)

活動中(状態0=休憩以外)で目的地未設定の場合:

```text
1. 活力(energy) <= 0 なら休憩探索 → 状態3(結果に関わらず)
2. 追加接客判定(下記5.2)が0 かつ 接客先探索が0 なら状態1、担当数+1
3. 補充先探索が0 なら状態2
4. 清掃先探索が0 なら状態4
5. それ以外は休憩探索 → 状態3
```

休憩中(状態0)は毎フレーム仕事を探すのではなく、`(時計>>1)%3==自分のスロット番号`
の巡回タイミングでのみ接客→補充→清掃の順に試す。

### 5.2 追加接客担当の判定(`0x80037F78`)

```text
現在の接客担当数 <= 0 なら 1(無条件追加)
担当数 >= 店舗要約+0x28-1 なら 1(無条件追加)
それ以外: 他の接客担当(状態1)の+0x1Eを合計し、roll1..100 <= 合計×2 なら追加しない(0)
```

### 5.3 補充(`0x8003B278`)

```text
A = 店員の補充能力(+0x1F、符号付きbyte)
roll1..100 > A なら補充なし
それ以外:
  要求量 = floor(A/10) + 1          # A=50なら6、A=100なら11
  実補充量 = min(要求量, 棚容量-現在在庫)
  在庫 += 実補充量
  補充費用 = floor(基準価格×原価係数/100) × 実補充量   # 販売価格は無関係
```

満杯(在庫>=容量)でも要求は発生するが実補充量・費用は0。

### 5.4 清掃(`0x80038894`)

```text
乱数1回: R%5 != 0 なら失敗(0)
乱数1回: roll1..100 <= 店員清掃能力(+0x21) なら成功(1)
成功時: 床コードを floor(tile/5)*5 へ変更(汚れ除去)、店舗の汚れフラグを0に
```

他の清掃担当のいる汚れマスは、`roll1..100 <= 2×他担当の+0x21`で候補から
除外(担当の重複防止、能力50以上では常に除外成立)。補充の担当重複防止も
同じ`2×能力`方式(`staff_targets.py`の`refill_reservations`参照)。

### 5.5 活力(エネルギー)増減(`0x800370EC`〜`0x800371A8`、`0x80036E10`〜`0x80036F30`)

```text
活動中: 乱数1回、R&3==0 なら活力-1。0以下になったら目的地クリア+フラグ
休憩中(活力<上限): 休憩設備ID48なら乱数1回・偶数で+1、ID49なら無条件+1
```

### 5.6 店員能力の増減(`0x8003AA58`)

```text
共通抽選 Q = (乱数%16==0)              # 1回だけ引き、同一呼出内で全能力が共有
各能力ごとに乱数を1回引く:
  roll1..100 <= 管理者の教育値M かつ 現在値<上限 かつ(現在値<通常成長境界 または Q)
  → 現在値+1
種別-1(月次の自然減衰): +0x1E, +0x1F, +0x21, +0x22 を各2以上なら-1(下限1)。+0x20は変化しない
```

種別2の清掃能力(+0x21)上昇は店舗の清潔さ>=100のときだけ判定(乱数消費も
その条件下のみ)。

## 6. 財務

### 6.1 三段階帳簿(店舗構造体内オフセット)

| 位置 | 意味 |
|---|---|
| +0xD88〜+0xD98 | 当日サイクルの帳簿(費用4項目+収入1項目、各32bit) |
| +0xD38〜+0xD48 | 月内累計(締めまでは倍率適用前) |
| +0xCE8〜+0xCF8 | 年内累計(月締めで補正後の値が加算される) |
| +0xD4C〜+0xD5C | 直前月の帳簿 |
| +0xCFC〜+0xD0C | 直前年の帳簿(総合評価の「年商」はここを参照) |

### 6.2 月次締めの8倍補正

```text
補正前利益 = 月内収入 − 費用1 − 費用2 − 費用3 − 費用4
資金 += 補正前利益 × 7            # 残り7倍分をまとめて資金へ反映(1倍分は既に個別取引で反映済み)
月内帳簿の5項目をそれぞれ8倍してから年内帳簿へ加算
月内帳簿を直前月の履歴へ移し、当月帳簿をリセット
```

内部月は4つの24時間サイクル(段階1〜4)で構成され、月初(段階1の0時0分)に
日次締め→月次締め→(1月なら)年次評価イベント予約の順で走る。

### 6.3 内部時刻の変換(`0x80019EB4`)

```text
年   = t // 69120 + 1
月   = (t // 5760) % 12 + 1
段階 = (t // 1440) % 4 + 1
時   = (t // 60) % 24
分   = t % 60
```

## 7. 街の成長(`0x8002BD54`、断片のみ復元)

### 7.1 影響値の加算(`-128〜127`の符号付き8bit、各マスに保持)

```text
正方形影響(自店中心8マス拡張): 該当マスへ min(100, 現在値+30)
非対称影響(上1マス+左右3マス拡張の十字、ただしcategory!=1のマスのみ):
    該当マスへ min(100, 現在値+10)
店舗影響(自店の価値を基準に拡張12マス、内側7マスは無条件・外側は乱数1/4で加算):
    strength = clamp(trunc(店舗価値/divisor), 0, 100)
    該当マスへ min(100, 現在値+strength)
```

### 7.2 建物レベルの昇格・降格

```text
影響値が正: roll1..100 <= 影響値 かつ レベル<25 なら レベル+1
影響値が負: roll1..100 <= -影響値 かつ レベル>=2 なら レベル-1
```

### 7.3 建替え判定(レベル条件付き、断片)

```text
レベル<4: 乱数1〜100が3未満 かつ 該当タイルの建物category==3(空き地等)なら取り壊し
レベル>=8: 乱数1〜100が3未満 なら新築種別を乱数で選び(レベル<15なら6種、以上なら7種から)、
           設置可否を確認して配置
```

## 8. ライバル(競合)経営AI — 月次処理(`0x8002A8E0`)

月初(段階1の0時0分)にのみ実行。自社・ライバルを合わせた有効店舗リストを
対象とする。

### 8.1 閉店判断

```text
各ライバル店舗について:
  直前月の利益が負なら連続赤字月数+1、黒字なら0にリセット
  保護条件(初出店直後 かつ 自社9店舗展開時の特殊条件)を除き、
  連続赤字月数>=6 なら閉店(土地・設備費用を回収、店員解除、建物を更地化)
```

一度の月次処理で最大1店舗だけ閉店する(閉店したら即return)。

### 8.2 出店判断(閉店が起きなかった場合)

```text
乱数&3 != 0 なら何もしない(出店判定自体を25%の頻度でしか行わない)
空き店舗スロットがなければ何もしない
出店規模 = 乱数 % size_limit   # size_limitは難易度設定で2/4/6段階
レイアウト・什器配置をテーブルから読み込み
店員を1〜3人、乱数で既存プールから採用(重複なし)
出店候補地を乱数で探索(建物レベル>=8かつ用途制約を満たす2×2区画)
費用(土地+建替え半額+設備+什器+在庫)を資金と比較し、資金不足なら中止
成立したら価格設定(27商品中、各1/16の確率で5刻みの値下げ)・店員配置・
開業処理を実行
```

**値下げは「各商品1/16の確率で0〜30円を5円刻みで下げる」というランダムな
価格競争であり、原価や需要を見た戦略的な値下げではない**(少なくともこの
関数単体では)。

## 9. 移植にあたっての注意

- 本プロジェクトの`src/simulation/*.ts`(2,632行)は、上記PS1解析(タイル単位の
  街・144客プロファイル・設備単位の店舗レイアウト等)よりもはるかに抽象化された
  モデルである。上記の数式をそのまま移植するには、客プロファイル表・設備表・
  街タイル表など、本プロジェクトにまだ存在しないデータ構造の新規設計が必要になる
  箇所が多い。
- `design/PRINCIPLES.md`は「史実を再現するだけでなく、別のコンビニ史を作れる」
  ことを明記しており、PS1版の忠実な再現は本来の方向性と**部分的に緊張関係にある**。

  大きい変更になる。着手する場合は独立した検討が必要。
